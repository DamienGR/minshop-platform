# Socle v0.3.0

Cette version est celle que la certification finale (jalon 10,
`docs/certification/plan.md`) éprouve en conditions réelles. Elle ferme
l'étape 0 de ce plan : tout ce que le dépôt pouvait prouver sans compte réel.

## Ce qui change

- **une sauvegarde avant chaque mise en production** (jalons 8 et 10) :
  `shopctl deploy --env production` prend une archive chiffrée, la copie dans
  le bucket privé `<worker>-backups` de l'environnement et ne migre qu'ensuite.
  Si la sauvegarde ou la copie échoue, rien n'est écrit. Aucune option ne saute
  cette étape ;
- **un bucket d'archives par environnement**, sur le compte de la boutique et
  dans sa juridiction (ADR 0005, note du 2026-10-06) : `provision` le crée,
  refuse qu'il soit public et lui pose une règle de cycle de vie à 90 jours ;
  `backup --upload` et `backup pull` y écrivent et en rapatrient ;
  `destroy` le supprime avec le reste ;
- **les droits RGPD d'une personne** (jalon 8) : `shopctl privacy export` et
  `shopctl privacy anonymize` (ADR 0017). Un effacement anonymise les
  commandes, il n'en supprime aucune ;
- **la supervision** : `shopctl monitor --env <env>` lit le taux d'erreur, le
  temps CPU et les quotas dans l'analytique Cloudflare, échoue au-delà de 1 %
  d'erreurs ou de 70 % d'un quota du plan gratuit. Les runbooks d'incident et la
  procédure de sortie d'un client sont dans `docs/operations/` ;
- **les portes distantes** : `npm run test:security:remote`,
  `test:browser:remote`, `test:load:remote`, `test:last-unit:remote`,
  `test:stripe:remote` et `test:email:remote` visent une boutique déployée par
  `BASE_URL` ;
- **un workflow nocturne** (`.github/workflows/nightly.yml`) : la suite
  complète et l'audit des dépendances partout ; dans une boutique, une
  sauvegarde de staging restaurée sur le runner (`restore --local`), les portes
  distantes, Stripe en mode test, un e-mail de test, et la lecture seule des
  seuils de production ;
- **une Content-Security-Policy partielle** : `object-src 'none'`,
  `base-uri 'self'` et `frame-ancestors 'none'`, posée par le middleware et par
  `public/_headers`. Le reste de la politique fait l'objet d'une dérogation
  datée.

## Migrations

**Aucune.** Les quarante-trois migrations de `v0.2.0` sont exactement celles de
`v0.3.0`. Un déploiement de cette version n'a pas de schéma à faire évoluer.

## À faire dans la boutique

Avant le prochain `deploy --env production`, qui refusera de partir sans eux :

```sh
npm run shopctl -- provision --env staging      # crée <worker>-staging-backups
npm run shopctl -- provision --env production   # crée <worker>-production-backups
npm run shopctl -- backup keygen                # seulement si l'agence n'a pas encore de clé
npm run shopctl -- repo                         # pose SHOPCTL_BACKUP_KEY dans les deux environnements GitHub
```

`provision` est idempotent : il ne crée que le bucket qui manque. `repo`
conserve une clé déjà posée, parce que c'est elle qui ouvre les archives prises
avec.

Pour que le workflow nocturne interroge staging, dans l'environnement GitHub
`staging` (la liste complète est en tête de `nightly.yml`) :

- `STAGING_URL` en variable, si le manifeste ne déclare pas de
  `cloudflare.stagingDomain` ;
- `CF_ACCESS_CLIENT_ID` et `CF_ACCESS_CLIENT_SECRET`, si staging est derrière
  Access ;
- `STRIPE_TEST_SECRET_KEY` (une clé de test, restreinte de préférence),
  `MINSHOP_ADMIN_PASSWORD` et la variable `NIGHTLY_EMAIL_TO` ;
- dans les secrets du dépôt, `MONITOR_CLOUDFLARE_API_TOKEN` et
  `MONITOR_CLOUDFLARE_ACCOUNT_ID` pour surveiller la production avec un jeton
  qui ne fait que lire.

Stripe, l'e-mail de test et la surveillance de production sont sautés avec un
avertissement quand leur secret manque. La sauvegarde et l'origine de staging,
elles, font échouer la nuit : sans elles, il n'y a rien à vérifier.

Gardez un mot de passe sur l'administration de staging : un jeton de service
Access ouvrirait une administration protégée par Access seul, et la porte de
sécurité distante le signale comme un échec.

## Compatibilité

Le manifeste ne change pas de forme ; `shopctl core upgrade` met `coreVersion` à
`0.3.0` tout seul.

La nouvelle CSP interdit d'afficher la boutique dans une `<iframe>` d'un autre
site et d'y utiliser `<object>` ou `<embed>`. Une boutique qui en a besoin le
signale avant de fusionner.

Aucune migration n'étant appliquée, un rollback applicatif vers `v0.2.0` reste
possible sans intervention sur la base.
