# Socle v0.2.0

Quatre pull requests séparent cette version de `v0.1.0`, qui livrait le socle
français, la CLI de création et le provisioning (jalons 0 à 6).

## Ce qui change

- **paiement et traitement de commande éprouvés** (jalon 7) : cycle de vie du
  règlement, réservations de stock, remboursements et idempotence du webhook
  Stripe sont tenus par des tests d'intégration contre le vrai schéma ;
- **la porte de sécurité** (jalon 8) : administration, Access, Turnstile,
  origine des formulaires, sessions, force brute, téléversements et en-têtes
  sont vérifiés contre le **Worker construit**, pas seulement unité par unité ;
- **sauvegarde et restauration** (jalon 8) : `shopctl backup` et
  `shopctl restore`, archives chiffrées, contrôlables sans Cloudflare et
  restaurables dans un autre compte (ADR 0005) ;
- **mise à niveau du socle et de la flotte** (jalon 9) : `shopctl core status`,
  `shopctl core upgrade`, `shopctl fleet …`, et la porte de publication qui a
  refusé de déplacer `v0.1.0` (ADR 0003, ADR 0016).

## Migrations

**Aucune.** Les quarante-trois migrations de `v0.1.0` sont exactement celles de
`v0.2.0` : rien n'a été ajouté, rien n'a été réécrit. Un déploiement de cette
version n'a pas de schéma à faire évoluer.

## À faire dans la boutique

Rien d'obligatoire : le manifeste, les bindings Wrangler et les secrets sont
inchangés depuis `v0.1.0` — mêmes variables, mêmes ressources, même
`wrangler.template.jsonc`.

Deux gestes recommandés une fois la mise à niveau fusionnée :

```sh
npm run shopctl -- backup keygen          # une fois par agence, la clé n'est jamais affichée
npm run shopctl -- backup --env production
```

La sauvegarde est ce que le jalon 8 ajoute de plus utile à une boutique déjà en
ligne, et elle est indépendante de cette version : la prendre maintenant vaut
mieux que la prendre le jour où elle sert.

## Compatibilité

Le manifeste ne change pas de forme ; `shopctl core upgrade` met `coreVersion` à
`0.2.0` tout seul. Le contrôle de compatibilité lit un pas mineur en 0.x comme
cassant (`checkCoreCompatibility`), donc une boutique qui fusionne le tag **sans**
ce bump verrait sa propre porte le refuser — c'est ce que la commande évite, et
c'est pourquoi elle refuse de fusionner sans mettre le manifeste à jour.

Aucune migration n'étant appliquée, un rollback applicatif vers `v0.1.0` reste
possible sans intervention sur la base.
