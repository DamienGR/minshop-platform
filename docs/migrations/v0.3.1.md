# Socle v0.3.1

Cette version corrige deux trous du socle v0.3.0, trouvés en préparant l'étape 1
de la certification (jalon 10, `docs/certification/plan.md`) et avant qu'un
compte réel les rencontre. La campagne part de cette version.

## Ce qui change

- **l'application Access de la preview, dans le manifeste** :
  `cloudflare.stagingAccessTeam` (le nom d'équipe Zero Trust, celui de
  `https://<équipe>.cloudflareaccess.com`) et `cloudflare.stagingAccessAud`
  (l'AUD de l'application). `provision` et `deploy` les rendent en
  `CF_ACCESS_TEAM_DOMAIN` et `CF_ACCESS_AUD` dans les `vars` du seul Worker de
  staging ; tout autre rendu les laisse vides, ce que l'administration lit comme
  « pas d'Access ». Sans eux, derrière Access, le Worker refusait toute
  assertion qu'il ne pouvait pas vérifier, et `/admin/setup` répondait 403 tant
  qu'aucun mot de passe n'existait. Les deux champs vont ensemble et demandent
  `cloudflare.stagingDomain` ; `deploy --env staging` avertit quand une preview
  privée n'en déclare aucun ;
- **un compte Cloudflare par environnement** : `cloudflare.productionAccountId`
  nomme le compte de la production quand ce n'est pas `accountId` — la
  production sur le compte du client, le staging sur celui de l'agence, les deux
  à la fois (ADR 0015). Toutes les commandes qui touchent un compte
  (`provision`, `deploy`, `destroy`, `backup`, `restore`, `privacy`,
  `monitor`) le lisent pour `--env production`, et `shopctl repo` pose dans
  chaque environnement GitHub son propre `CLOUDFLARE_ACCOUNT_ID`. Absent, rien ne
  change : la production vit sur `accountId`.

## Migrations

**Aucune.** Les quarante-trois migrations de `v0.3.0` sont celles de `v0.3.1`.

## À faire dans la boutique

- une preview derrière Access : ajouter sous `cloudflare:` le nom d'équipe et
  l'AUD de l'application, puis `shopctl deploy --env staging` ;
- une production sur le compte du client : ajouter
  `productionAccountId: <identifiant du compte>` sous `cloudflare:`, puis
  relancer `shopctl repo` pour que l'environnement `production` reçoive ce
  compte ;
- sinon, rien.

## Compatibilité

Le manifeste gagne trois champs facultatifs et ne change pas de version de
schéma : un manifeste v0.3.0 reste valide tel quel, et `shopctl core upgrade`
met `coreVersion` à `0.3.1` tout seul.

Le `wrangler.jsonc` rendu porte désormais `CF_ACCESS_TEAM_DOMAIN` et
`CF_ACCESS_AUD` dans ses `vars`, vides sauf sur une preview qui les déclare. Une
boutique qui posait ces deux valeurs à la main dans le tableau de bord les
perdait déjà à chaque `wrangler deploy` ; elle les déclare maintenant dans le
manifeste.

Aucune migration n'étant appliquée, un rollback applicatif vers `v0.3.0` reste
possible sans intervention sur la base.
