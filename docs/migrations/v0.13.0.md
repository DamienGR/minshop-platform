# Socle v0.13.0

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version laisse l'acheteur saisir un code promo ou une carte cadeau dans
le panier, l'achat immédiat ou la page de commande, et l'applique quel que
soit le moyen de paiement ; les codes se créent dans un nouvel écran Admin →
Codes promo (plan §13.32, ADR 0033). Une migration additive (0065), d'où une
version mineure. Travail d'après le pilote, hors des jalons 0 à 10.

## Ce qui change

- **Admin → Codes promo** : créer un code (pourcentage ou montant fixe des
  articles, minimum d'achat, dates, nombre d'utilisations), une carte cadeau
  (montant fixe, une utilisation, code tiré au hasard), modifier, désactiver,
  supprimer ; la liste dit l'état et les utilisations de chaque code.
- **Le champ « Code promo ou carte cadeau »** dans le panier (« Appliquer »,
  « Retirer le code »), l'achat immédiat et l'étape d'adresse de `/checkout`,
  dès qu'un code est actif et tant que « Codes promo » est allumé dans
  Réglages (ancien « Codes de remise », même interrupteur, même défaut). Le
  récapitulatif montre la remise avant le paiement.
- **Tous les moyens de paiement l'appliquent** : la carte reçoit la remise
  toute faite sur la page de Stripe, le virement, Lightning, OpenNode et la
  démonstration demandent le total net. Un panier que le code paie en entier
  passe par la carte ou la démonstration ; les autres moyens le refusent.
- **Le champ de code de la page Stripe disparaît** : les codes du tableau de
  bord de Stripe ne s'appliquent plus (voir plus bas).
- **Le code paraît sur la commande** : « Remise (NOEL10) » dans l'e-mail de
  confirmation, la page de commande de l'acheteur, les pages de paiement de
  la démonstration et du virement, et la fiche commande de l'administration.
- **L'API JSON** (`/api/checkout`) prend `discount_code` et répond
  `discount: { code, amount_cents }` avec un `total_cents` net ; un code
  refusé répond 400 (`reason: "discount_code"`), un code pris entre-temps
  409. `GET /api/checkout` dit `discount_codes`.
- **Le réglage « Codes promo » ne demande plus Stripe** : il vaut pour tous
  les moyens de paiement.
- `/api/discount` et `/express` rejoignent le seau `checkout` du limiteur de
  débit.

## Migrations

Une, additive (ADR 0006). `shopctl deploy` l'applique après avoir sauvegardé
la production ; ne jamais l'appliquer à la main.

- `migrations/0065_discount_codes.sql` : la table `discount_codes` ;
  `discount_code_id` et `discount_code` sur `checkout_reservations` et sur
  `orders` ; `pending_payments.discount_cents` (0 par défaut) ; deux index
  partiels sur `discount_code_id`. Aucune ligne réécrite.

## À faire dans la boutique

- **une boutique qui utilisait des codes promotionnels créés dans Stripe** :
  les recréer dans Admin → Codes promo avant ou juste après le déploiement ;
  la page de Stripe ne propose plus son champ. Les commandes passées gardent
  leur remise ;
- **une boutique qui vend des cartes cadeaux** (et non les offre) : la TVA
  de la commande est calculée sur le total payé, carte déduite, comme pour
  une remise ; pour une carte vendue, elle est due sur le prix plein. Faire
  valider le traitement par l'expert-comptable avant la première vente
  (ADR 0033) ;
- **une boutique qui ne veut pas du champ** : il ne paraît qu'avec un code
  actif ; pour le cacher même avec des codes, éteindre « Codes promo » dans
  Réglages ;
- **un thème qui restyle le panier ou la page de commande** : le champ est
  `DiscountCodeField` (`src/features/discounts/`), dans
  `[data-discount-field]`, et la ligne de remise des récapitulatifs porte
  `data-discount-line` ;
- **une suite propre à la boutique qui écrit à la main un schéma
  `orders`, `checkout_reservations` ou `pending_payments`** : ajouter les
  colonnes de la migration 0065, ou passer par `applyMigrations()`
  (`test/helpers/d1-schema.mjs`) ;
- **une boutique qui avait modifié** `src/pages/cart.astro`,
  `src/pages/express.astro`, `src/pages/checkout.astro`,
  `src/pages/api/checkout.ts`, `src/features/payments/stripe.ts` ou
  `src/features/orders/reservations.ts` verra un écart à la montée : y
  reporter sa modification.

## Guide administrateur

- nouveau chapitre « Codes promo » : créer un code, créer une carte cadeau,
  suivre les utilisations, désactiver ou supprimer un code, les codes créés
  dans Stripe ;
- Réglages : l'interrupteur « Codes de remise » devient « Codes promo ».

## Compatibilité

Les manifestes v0.12.x restent valides tels quels ; `features.promoCodes` ne
change pas de sens pour la boutique. `shopctl core upgrade` met `coreVersion`
à `0.13.0` tout seul ; une boutique qui fusionne le tag à la main doit le
faire elle-même, sans quoi la porte des manifestes refuse un manifeste en
`0.12.x` sur un socle en `0.13.0`.

La migration n'enlève rien : le Worker v0.12.0 fonctionne sur le nouveau
schéma, et un rollback applicatif reste possible sans toucher à la base. Ce
que v0.12.0 ne sait pas faire pendant le rollback :

- **il ignore les codes de la boutique** : plus de champ dans le panier, et la
  page de Stripe rouvre son propre champ, pour les codes du tableau de bord ;
- **une réservation ou un paiement en attente créé par v0.13.0 avec un code**
  se règle sous v0.12.0 sans recopier le code sur la commande ; la remise
  d'un virement, d'une facture Lightning ou d'une démonstration en cours est
  perdue dans le détail de la commande (`discount_cents` à 0) alors que le
  montant payé est bien net. Le marchand le lit dans le total.
