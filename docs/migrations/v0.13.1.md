# Socle v0.13.1

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version change ce que le dépôt de flotte du compte mutualisé (ADR 0019)
publie. Ce dépôt est public : n'importe qui lit ses journaux, et n'importe quel
compte GitHub télécharge ses artefacts. Les rapports de shopctl y donnaient
deux fois par nuit le nombre de lignes de chaque table de chaque boutique,
`orders` comprise, le trafic mesuré par `monitor`, et l'identifiant du compte
en clair dans les artefacts. Aucune migration, aucun changement du Worker,
d'où une version corrective. Travail d'après le pilote, hors des jalons 0 à 10.

## Ce qui change

- **Les rapports restent sur le runner.** Les workflows Deploy et Nightly de
  la flotte écrivent le JSON et le texte de chaque commande shopctl dans des
  fichiers. Le journal et l'artefact ne reçoivent que le résumé qu'en tire
  `.github/fleet/shops.mjs report`, champ par champ : l'issue, les contrôles
  en échec, l'archive, le bookmark Time Travel et la version de retour d'un
  déploiement. Quand la commande échoue, le résumé ajoute son erreur et ses
  lignes ✗ et !. Les artefacts gardent leurs noms (`deploy-<slug>-production-…`)
  et ne contiennent plus que `*.summary.json`.
- **Le jeton de surveillance passe dans un environnement `monitor`**, limité
  à la branche par défaut comme `backup`. Son « D1 en lecture » lit les bases
  de toutes les boutiques du compte : en secret du dépôt, il était lisible
  depuis n'importe quelle branche. `shopctl fleet repo` crée l'environnement,
  y pose les deux secrets, et nomme ceux qui restent dans le dépôt avec la
  commande qui les retire, sans jamais les supprimer.
  `shopctl certify` les attend là pour une boutique de la flotte, et
  l'avertit tant qu'ils restent aussi dans le dépôt.
- **Les jetons du compte ne sont plus donnés qu'aux étapes qui lancent
  shopctl.** `npm ci` tourne sans les scripts d'installation des dépendances
  (`--ignore-scripts`), et aucun checkout ne garde son jeton dans la
  configuration git (`persist-credentials: false`).
- Rien ne change pour une boutique sur son propre compte : ses workflows sont
  ceux du socle, inchangés.

## Migrations

- aucune.

## À faire dans la boutique

- rien dans la boutique elle-même : `shopctl core upgrade --to v0.13.1`
  apporte les modèles de flotte et le nouveau `certify` ;
- **dans le dépôt de flotte**, avec le shopctl de v0.13.1 et dans cet ordre :
  1. `shopctl fleet init`, puis committer et pousser les trois fichiers
     réécrits ;
  2. `shopctl fleet repo --reviewer <login>` avec `CLOUDFLARE_API_TOKEN_MONITOR`
     dans l'environnement : il crée `monitor` et y pose le jeton. Toujours
     avec `--reviewer` : sans lui, `production` est reposé sans relecteur ;
  3. monter les boutiques de la flotte en v0.13.1 : le `certify` d'une
     boutique restée en v0.13.0 cherche encore les secrets dans le dépôt ;
  4. retirer les secrets du dépôt que `fleet repo` a nommés :
     `gh secret delete MONITOR_CLOUDFLARE_API_TOKEN --repo <flotte>` et
     `gh secret delete MONITOR_CLOUDFLARE_ACCOUNT_ID --repo <flotte>` ;
- **les journaux et artefacts déjà publiés** restent en ligne, jusqu'à
  90 jours pour les artefacts du Deploy. Les supprimer est irréversible et
  reste au choix de l'agence. Supprimer les journaux sans les runs garde
  l'historique que `certify` lit :

  ```sh
  gh api --paginate repos/<flotte>/actions/artifacts -q '.artifacts[].id' \
    | xargs -I{} gh api -X DELETE repos/<flotte>/actions/artifacts/{}
  gh run list --repo <flotte> --limit 500 --json databaseId -q '.[].databaseId' \
    | xargs -I{} gh api -X DELETE repos/<flotte>/actions/runs/{}/logs
  ```

## Guide administrateur

- inchangé : aucun écran de l'administration ne change.

## Compatibilité

Les manifestes v0.13.0 restent valides tels quels. `shopctl core upgrade` met
`coreVersion` à `0.13.1` tout seul ; une boutique qui fusionne le tag à la main
doit le faire elle-même, sans quoi la porte des manifestes refuse un manifeste
en `0.13.0` sur un socle en `0.13.1`.

Le Worker est celui de v0.13.0 : un rollback applicatif vers v0.13.0 ne change
rien au site. Les nouveaux workflows de flotte lancent les mêmes commandes
shopctl qu'avant, et une boutique encore en v0.13.0 s'y déploie et s'y
sauvegarde comme avant. Tant que `fleet repo` n'a pas créé `monitor`, GitHub
le crée vide au premier Nightly et les jobs lisent encore les secrets du dépôt.
