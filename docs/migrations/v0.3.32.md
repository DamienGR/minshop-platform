# Socle v0.3.32

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version pose la garde d'isolement du compte Cloudflare mutualisé et le
domaine du commerçant par Cloudflare for SaaS (ADR 0019, lots 2 et 3 du plan
§13.1). Travail d'après le pilote, hors des jalons 0 à 10.

## Ce qui change

### La garde d'isolement

Sur un compte partagé, le nom d'une ressource ne prouve plus à quelle boutique
elle appartient.

- **un marqueur de boutique dans chaque base D1.** `shopctl provision` écrit
  dans la table `_minshop_owner` le dépôt de la boutique (son `origin`,
  `propriétaire/dépôt` en minuscules) et son slug, dès que la base existe. Une
  base antérieure au marqueur est revendiquée au premier passage, avec une
  ligne qui le dit.
- **une base marquée pour une autre boutique est refusée** (code 4) avant toute
  écriture par `provision`, et avant toute lecture par `deploy`, `destroy`,
  `restore`, `backup`, `privacy`, `admin password` et `certify`. Une base sans
  marqueur n'est qu'un avertissement. Un arbre sans `origin` face à une base
  marquée pour un dépôt est refusé aussi : il ne peut pas prouver qu'il est ce
  dépôt.
- **`shopctl provision --claim <slug>`**, le slug saisi, réécrit le marqueur
  d'une base marquée pour un autre dépôt : c'est le cas d'un dépôt renommé ou
  transféré.
- **`shopctl fleet status` et `fleet verify`** signalent en échec deux boutiques
  du registre dont les manifestes revendiquent un même nom : Worker, base,
  bucket ou nom d'hôte.
- **`shopctl new` refuse avant de cloner** (code 3) un slug que le `fleet.json`
  trouvé en remontant depuis le répertoire courant inscrit déjà, ou un nom
  qu'un manifeste de ce registre dérive déjà (domaine compris).
- le marqueur n'entre ni dans une sauvegarde, ni dans une restauration, ni dans
  un export RGPD.

### Le domaine du commerçant par Cloudflare for SaaS

- **`cloudflare.saasZone`**, champ facultatif du manifeste : la zone SaaS de
  l'agence sur le compte mutualisé. Quand le domaine de production est hors de
  cette zone, la production rend une route `<domaine>/*` sur la zone au lieu
  d'un domaine personnalisé, et `workers.dev` reste fermé. Le staging n'y passe
  jamais. Une boutique sans ce champ ne change pas.
- **`shopctl provision --env production`** crée le nom d'hôte personnalisé du
  commerçant sur la zone (validation HTTP, TLS 1.2 au moins) et donne la ligne à
  lui transmettre : `CNAME <domaine> → <origine de repli>`.
- **`shopctl deploy --env production`** refuse un nom d'hôte absent, ou encore en
  attente du DNS sauf `--skip-smoke` (premier déploiement avant la bascule du
  domaine).
- **`shopctl destroy --env production`** supprime le nom d'hôte après le Worker.
- **`shopctl certify`** juge le nom d'hôte dans le groupe du compte.
- Ces trois commandes parlent à l'API de Cloudflare avec `CLOUDFLARE_API_TOKEN`
  (« Zone : Read » et « SSL and Certificates : Edit » sur la zone SaaS) :
  wrangler ne gère pas les noms d'hôte personnalisés.
- Router plusieurs noms d'hôte d'une même zone vers plusieurs Workers reste à
  prouver par l'essai réel du lot 3, avant qu'une boutique n'en dépende.

## Migrations

- aucune. La table `_minshop_owner` n'est pas une migration : elle appartient à
  l'outillage, qui la crée lui-même (`CREATE TABLE IF NOT EXISTS`).

## À faire dans la boutique

- relancer `shopctl provision --env <env>` sur chaque environnement déployé,
  depuis un clone du dépôt de la boutique : il pose le marqueur sans rien
  recréer. D'ici là, `deploy` et les autres commandes avertissent seulement.
- rien pour le domaine : `cloudflare.saasZone` ne concerne que les boutiques
  du compte mutualisé, qui le déclareront à leur arrivée.

## Compatibilité

Le manifeste gagne un champ facultatif, `cloudflare.saasZone` : un manifeste
v0.3.31 reste valide tel quel, et `shopctl core upgrade` met `coreVersion` à
`0.3.32` tout seul. Un manifeste qui déclare `saasZone` n'est pas lisible par
un socle plus ancien.

Aucune migration : un rollback applicatif vers `v0.3.31` reste possible sans
intervention sur la base. Le Worker ne lit pas `_minshop_owner`, et un
`shopctl` plus ancien l'ignore.
