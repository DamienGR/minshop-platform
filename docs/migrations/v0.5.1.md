# Socle v0.5.1

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version corrige ce que les boutiques de démonstration et la première
boutique réelle ont relevé en montant en v0.5.0 : l'outillage d'une boutique
(tickets #80 à #83, #86), le contrat des thèmes (ticket #84), un commentaire
trompeur (ticket #85), les tests du contrat de vitrine dans une boutique qui
dessine les nouvelles données, le socle de test d'une boutique en franchise
(ticket #173) et les insécables des textes du thème (ticket #175). Aucune
migration, rien d'obligatoire dans une boutique, d'où une version corrective.
Travail d'après le pilote, hors des jalons 0 à 10.

## Ce qui change

- **Les insécables d'un texte du thème d'une ligne sont gardés**
  (ticket #175). Seules les espaces sécables sont fondues : une fine
  insécable avant « ? » ou un espace insécable dans « 15 € » restent en
  place, qu'ils viennent du défaut du thème ou de ce que tape le marchand.
  Rien ne change pour les textes déjà enregistrés. Une boutique qui avait
  contourné le défaut peut garder son contournement.
- **Dependabot n'ouvre plus de pull request dans une boutique**
  (ticket #81). `.github/dependabot.yml` est maintenant un fichier généré :
  celui d'une boutique met `open-pull-requests-limit` à 0, car
  `package.json` et `package-lock.json` sont des fichiers du cœur, qui
  bougent avec `shopctl core upgrade`. Les alertes de vulnérabilité restent.
- **`shopctl core upgrade` nomme les écarts du cœur à approuver**
  (ticket #86). Un fichier du cœur que la boutique avait modifié, et que la
  version modifie aussi, sort de la fusion sans être la copie de personne :
  le job « File ownership » de la pull request le refusera. La montée le dit
  maintenant avant la CI, fichier par fichier, avec la façon de l'approuver
  (étiquette `core-change` ou ligne `Approves-core-change:`), et la pull
  request le liste.
- **`shopctl repo --no-environments`** (ticket #82) crée le dépôt d'une
  boutique qu'aucun compte Cloudflare ne porte encore (maquette,
  démonstration), sans environnement ni secret ; `shopctl new --create-repo
  --no-environments` aussi. Sans compte et sans l'option, `shopctl repo`
  refuse désormais avant de rien créer.
- **La page d'accueil GitHub de la boutique** (ticket #83) :
  `.github/README.md` appartient à la boutique, et `shopctl new` l'écrit.
  GitHub l'affiche avant le `README.md` racine, qui reste la documentation
  du socle.
- **Le thème connaît la route du catalogue et l'adresse de la fiche**
  (ticket #84) : `CatalogPageModel.route` (`'home'` ou `'products'`) et
  `ProductDetailModel.href` (`CUSTOMIZING.md`). Les thèmes livrés n'en
  dessinent rien.
- **Le Nightly d'une boutique pas encore en ligne reste vert** (ticket #80) :
  ses avertissements disent que l'absence de jeton est attendue. C'était déjà
  le cas depuis v0.3.29 ; un test le fixe.
- **`orderNumber`** ne numérote que les commandes antérieures aux références
  `ord_` (ticket #85) : les commentaires le disent maintenant.
- **Le contrat de vitrine ne refuse plus le thème d'une boutique** qui
  dessine les données de la v0.5.0 (variantes des cartes, étiquettes,
  catégories, produit mis en avant, textes du thème) : les cinq tests qui
  exigent un rendu inchangé ne tiennent plus que les thèmes du socle.
- **Le socle de test bâti depuis une boutique est un cœur** (ticket #173) :
  il prend les `storeOverrides` vides du socle, si bien que `npm run verify`
  repasse dans une boutique en franchise en base, et il laisse de côté le
  manifeste et la page d'accueil de la boutique.

## Migrations

Aucune.

## À faire dans la boutique

- rien d'obligatoire ;
- **`.github/dependabot.yml`** : la montée le re-rend pour la boutique.
  Dans la pull request de montée, il doit être le rendu « boutique »
  (`open-pull-requests-limit: 0`). Les pull requests Dependabot déjà
  ouvertes dans le dépôt de la boutique sont à fermer sans les fusionner.
  Laisser « Dependabot security updates » éteint dans les réglages du dépôt ;
- **`src/store.config.ts`** : seul son commentaire d'en-tête change (la ligne
  d'exemple `orderNumber` disparaît). C'est un fichier de la boutique : en cas
  de conflit, garder la version de la boutique ;
- **`.github/README.md`** : une boutique existante peut s'en écrire un, à la
  main ; il lui appartient, et la porte de neutralité ne le lit pas ;
- une boutique qui avait reporté à la main le correctif du socle de test
  (ticket #173) ou celui du contrat de vitrine reçoit le même contenu, et
  la fusion n'y voit pas de conflit.

## Compatibilité

Les manifestes v0.5.0 restent valides tels quels. `shopctl core upgrade` met
`coreVersion` à `0.5.1` tout seul ; une boutique qui fusionnerait le tag à la
main doit le faire elle-même.

Aucune migration : un rollback vers v0.5.0 ne touche pas à la base. Pendant
le rollback, un texte du thème d'une ligne enregistré perd à nouveau ses
insécables, et un thème de boutique qui lit `route` ou `href` ne les trouve
plus.
