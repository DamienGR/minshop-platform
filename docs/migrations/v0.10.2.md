# Socle v0.10.2

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version laisse un thème placer un ornement dans le titre d'une page
(ticket #251, PR #252) : la marchande écrit `[feuille]` dans le titre, le thème
dessine la feuille à cet endroit, et le socle retire le code partout où il
imprime ce titre en texte seul. Aucune migration, rien à changer dans une
boutique dont le thème ne déclare pas de code, d'où une version corrective.
Travail d'après le pilote, hors des jalons 0 à 10 (plan §13.29).

## Ce qui change

- **`src/themes/<id>/titles.ts`, facultatif** : `export const titleMarks =
  ['feuille']`. Chaque code est un mot en minuscules (lettres et chiffres,
  traits d'union entre eux), écrit sans ses crochets, vingt au plus. Il est lu
  au build comme `texts.ts` et `pageModels.ts` ; un code invalide est écarté,
  et `test/storefront/titleMarks.test.ts` échoue sur la déclaration.
- **Le gabarit reçoit le titre tel qu'il est écrit**, codes compris
  (`ContentPageModel.title`, `ModelPageModel.title`, les zones d'un modèle) :
  dessiner l'ornement revient au thème.
- **Le socle retire les codes là où il imprime le titre d'une page en texte
  seul** (`plainTitle()`, `src/features/titleMarks/marks.ts`) : `<title>`,
  `og:title` et `twitter:title` de la page et de son aperçu, `llms.txt`, le
  texte d'un menu sans libellé (vitrine, aperçu, écran Navigation), la
  description qu'une page à modèle au corps vide tire de ses zones, et le
  **Titre pour Google** grisé de l'éditeur. La casse n'importe pas et des
  espaces entre les crochets sont tolérées ; un **Titre pour Google** rempli
  reste pris tel quel, et un lien Markdown `[mot](…)` n'est pas un code.
- **L'éditeur de page annonce les codes** sous **Titre** (« Codes du thème :
  [feuille] »), pour un thème qui en déclare.
- **Rien ne change pour un thème sans déclaration** : les thèmes livrés n'en
  déclarent aucun. Les noms de produit et de catégorie gardent leurs
  crochets, puisqu'ils partent dans les commandes, Stripe et les e-mails.

## Migrations

- aucune.

## À faire dans la boutique

- rien d'obligatoire ;
- **un thème qui veut un ornement dans le titre d'une page** : déclarer ses
  codes dans `src/themes/<id>/titles.ts` et dessiner l'ornement depuis
  `model.title` dans ses gabarits (`CUSTOMIZING.md`, « Ornaments in a page's
  title »). Ce que le thème imprime lui-même en texte seul (un résumé, un menu
  construit depuis les titres) demande sa propre copie de la règle, puisqu'un
  thème n'importe pas de code du socle ;
- **un code de la boutique qui appelle** `toMenuItem()`, `groupMenus()`,
  `getMenus()`, `readDocumentRows()` ou `buildPageView()` : leur passer les
  codes du thème (`activeTitleMarks`, ou `[]` dans un test), désormais requis ;
  un `PageView` construit à la main prend `titleText`. Sans quoi `astro check`
  le refuse ;
- **une boutique qui avait modifié** `src/middleware.ts`,
  `src/features/navigation/db.ts`, `src/features/pages/view.ts`,
  `src/features/storefront/reads.ts`, `src/pages/llms.txt.ts`,
  `src/pages/pages/[slug].astro`, `src/pages/admin/navigation.astro`,
  `src/pages/admin/pages/[id]/edit.astro` ou
  `src/pages/admin/pages/[id]/preview.astro` verra un écart à la montée : y
  reporter sa modification.

## Compatibilité

Les manifestes v0.10.1 restent valides tels quels. `shopctl core upgrade` met
`coreVersion` à `0.10.2` tout seul ; une boutique qui fusionne le tag à la main
doit le faire elle-même, sans quoi la porte des manifestes refuse un manifeste
en `0.10.1` sur un socle en `0.10.2`.

La base ne bouge pas : un rollback applicatif vers v0.10.1 reste possible. Un
thème qui déclare `titles.ts` y retrouve ses codes en toutes lettres dans le
titre du document, `llms.txt` et les menus sans libellé ; le fichier lui-même
ne gêne pas le build, rien ne le lisant.
