# Socle v0.10.1

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version retire du Worker un fichier de test qu'Astro servait comme une
page (PR #249). Aucune migration, rien à changer dans une boutique, d'où une
version corrective. Travail d'après le pilote, hors des jalons 0 à 10.

## Ce qui change

- **L'adresse `/sitemap.xml.test` disparaît** et répond 404. Astro construit
  en route tout fichier de `src/pages/` dont le nom ne commence pas par `_`,
  un test compris : `src/pages/sitemap.xml.test.ts` était servi depuis
  v0.1.0 et répondait 500, puisque `describe` lève hors d'un run vitest. Un
  robot qui la visitait comptait dans le taux d'erreur que `shopctl monitor`
  surveille.
- **Le Worker perd environ 126 KiB compressés** : la route embarquait vitest
  et chai. Une boutique mesurée à 1004 KiB sur le budget de 1024 KiB de
  `scripts/check-deploy.mjs` repasse autour de 878 KiB.
- **`sitemap.xml` ne change pas** : la règle qui le compose (`sitemapLocs()`)
  passe dans `src/features/seo/sitemap.ts`, son test à côté, et la route
  l'importe.
- **Un fichier de test sous `src/pages/` est refusé** par
  `test/scripts/page-routes.test.mjs`, donc par `npm run verify`.

## Migrations

- aucune.

## À faire dans la boutique

- **déployer** : rien d'autre, la montée (`shopctl core upgrade --to
  v0.10.1`) apporte le correctif ;
- **une boutique qui a posé un test dans `src/pages/`**, dans ses propres
  fichiers : `npm run verify` le refuse désormais. Le déplacer, avec la
  logique qu'il teste, sous `src/features/` ou `test/` ;
- **une boutique qui avait modifié** `src/pages/sitemap.xml.ts` verra un écart
  à la montée : y reporter sa modification, en important `sitemapLocs()`
  depuis `src/features/seo/sitemap.ts`.

## Guide administrateur

- inchangé : aucun écran de l'administration ne change.

## Compatibilité

Les manifestes v0.10.0 restent valides tels quels. `shopctl core upgrade` met
`coreVersion` à `0.10.1` tout seul ; une boutique qui fusionne le tag à la main
doit le faire elle-même, sans quoi la porte des manifestes refuse un manifeste
en `0.10.0` sur un socle en `0.10.1`.

Aucun changement de schéma : un rollback applicatif vers v0.10.0 reste
possible et rend l'adresse `/sitemap.xml.test`, en 500.
