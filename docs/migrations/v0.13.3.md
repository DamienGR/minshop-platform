# Socle v0.13.3

<!-- Ce que cette version demande à une boutique qui la prend. Lu par
     `shopctl core upgrade` et repris dans la pull request de mise à niveau. -->

Cette version prépare le rapport trimestriel que l'agence envoie au commerçant
(ADR 0035) : ses ventes, les évolutions de sa boutique, sa place dans Google et
ses visiteurs, dans une issue du dépôt de la boutique, le 5 de chaque
trimestre. Une commande de shopctl et un workflow du dépôt de flotte, rien dans
la boutique elle-même, sans migration : d'où une version corrective. Travail
d'après le pilote, hors des jalons 0 à 10 (plan §13.34).

## Ce qui change

- **`shopctl report --env production`** : le rapport d'un trimestre, en
  lecture seule partout. Ventes lues dans la base de production par des
  agrégats seulement (commandes payées, chiffre d'affaires TTC,
  remboursements, panier moyen, acheteurs distincts, produits en tête) ;
  évolutions tirées de l'historique git de la boutique et des notes des
  versions du socle franchies ; référencement par Google Search Console
  (compte de service, `GSC_SERVICE_ACCOUNT_JSON`) ; fréquentation par Umami
  (le site de Réglages → Mesure d'audience, `UMAMI_API_KEY`). Une source
  illisible ou non raccordée est dite, et le rapport sort avec les autres.
  `--out` écrit `rapport.md` et `rapport.json` ; `--publish` ouvre ou réécrit
  l'issue « Rapport trimestriel — <trimestre> » du dépôt de la boutique, et
  refuse, avant toute lecture, un dépôt qui n'est pas privé ou sans issues.
- **Le workflow « Quarterly report » du dépôt de flotte**, écrit par
  `shopctl fleet init` : le 5 janvier, avril, juillet et octobre, le rapport
  de chaque boutique de `fleet.json`, avec le shopctl de son socle, depuis
  l'environnement GitHub `report` que pose `shopctl fleet repo`. Le journal et
  l'artefact, publics, ne portent que le trimestre, l'issue et les sources en
  échec. Lancé à la main : l'aperçu du trimestre en cours, une seule boutique.
- **`fleet.json`** accepte `"reportSince": "AAAA-MM-JJ"`, le début du suivi
  d'une boutique.
- Une ligne `Pour le client : …` dans les commits d'une pull request de la
  boutique devient la phrase du message au commerçant ; `Pour le client : -`
  l'en écarte.

## Migrations

- aucune.

## À faire dans la boutique

- rien d'obligatoire : la boutique ne change pas ;
- **pour recevoir le rapport** : un dépôt privé avec ses issues
  (`gh repo edit <dépôt> --enable-issues`, `shopctl repo` les crée sans), le
  compte de service de l'agence en « Restreint » sur sa propriété Search
  Console, et sa ligne `reportSince` dans `fleet.json`
  (`docs/operations/rapport-trimestriel.md`) ;
- **dans le dépôt de flotte**, une fois, avec ce socle : `shopctl fleet init`,
  commit et push, puis `shopctl fleet repo --reviewer <login>` avec, en plus
  des jetons habituels, `CLOUDFLARE_API_TOKEN_MONITOR`, `REPORT_ISSUES_TOKEN`
  et, s'il y a lieu, `GSC_SERVICE_ACCOUNT_JSON` et `UMAMI_API_KEY`.

## Guide administrateur

- inchangé : aucun écran de l'administration ne change.

## Compatibilité

Les manifestes v0.13.2 restent valides tels quels. `shopctl core upgrade` met
`coreVersion` à `0.13.3` tout seul ; une boutique qui fusionne le tag à la main
doit le faire elle-même, sans quoi la porte des manifestes refuse un manifeste
en `0.13.2` sur un socle en `0.13.3`.

La base ne bouge pas : un rollback applicatif vers v0.13.2 reste possible. Une
boutique sous v0.13.3 est écartée du workflow « Quarterly report », comme le
Deploy de la flotte écarte une boutique trop ancienne.
